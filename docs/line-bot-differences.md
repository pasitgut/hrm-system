# ส่วนที่ต่างจาก Google Apps Script เดิม

เอกสารนี้เป็นรายการความต่างปัจจุบัน หลังผู้ใช้ยืนยันให้กลับไปลงทะเบียนด้วยรหัสพนักงานและใช้ Flex ต้นฉบับ ดู [mapping ทุกฟังก์ชัน](line-bot-function-mapping.md) และ [งานก่อนเปิดจริง](line-bot-pending.md) ประกอบ

## ส่วนที่คืนตามต้นฉบับแล้ว

- พิมพ์ ลงทะเบียน แล้วกรอกรหัสพนักงาน เก็บ LINE user ID ใน employees.line_uid สำหรับครั้งต่อไป ไม่ต้องขอ OTP หรือกดเชื่อมจากหน้า HRM
- หากเริ่มส่งคำขอลาโดยยังไม่ลงทะเบียน ระบบถามรหัส แล้วกลับไปแสดงเมนูลาอัตโนมัติเมื่อลงทะเบียนสำเร็จ
- ใช้ Flex เดิมสำหรับประเภทลา วัน/เวลา ยืนยัน สำเร็จ แจ้งผู้อนุมัติ แจ้งผล และนัดหมาย สี/ข้อความ/ขนาด/layout นำมาจากต้นฉบับ
- แจ้งเหตุผล ระยะเวลา ช่องทาง รหัสพนักงาน สถิติลา และชื่อผู้พิจารณาครบตาม field เดิม
- แจ้งผู้อนุมัติเมื่อเจ้าของยกเลิก และส่งผลการพิจารณาให้พนักงานกับผู้พิจารณา

## Backend และข้อมูลที่ต้องต่างเมื่อย้ายฐาน

| ประเด็น | ต้นฉบับ | ระบบใหม่และเหตุผล |
|---|---|---|
| ตัวระบุใบลา | เลขแถว Sheets และ Lเลขแถว | UUID ของ leave_requests; การ์ดแสดง L ตามด้วย UUID 8 ตัวแรก ขณะที่ปุ่มใช้ UUID เต็ม ไม่เดาเลขแถวเดิม |
| ข้อมูลในปุ่ม | action/row/type | เพิ่ม draft และ revision ที่มองไม่เห็น เพื่อไม่ให้ปุ่มเก่าอนุมัติข้อมูลที่เปลี่ยนไปแล้ว |
| ชื่อประเภทลา | คงที่ ลากิจ/ลาป่วย/ลาวันเกิด | หน้าตาคง 3 ปุ่มเดิม แต่ต้อง map ไป leave_types ที่ active ใน HRM ถ้าไม่มีประเภทนั้นจะไม่สร้างข้อมูลประเภทลาจากการเดา |
| สถิติและโควตา | ปี hardcode 2026 และ 6/1 วัน | ใช้ปีปัจจุบันใน Bangkok และโควตาของ HRM รวม tenure; หน้าตา field เดิม แต่ค่าต้องเป็นจริงตามฐานหลัก |
| ที่มาคำขอ | คอลัมน์ M ของ Sheets | snapshot ใน job: Line สำหรับ bot, Web สำหรับ HRM ไม่มีการเพิ่ม source column ลง leave_requests |
| กลุ่มผู้อนุมัติ | ADMIN_IDS | users.permissions ที่มี leave.approve และบัญชียังใช้งานได้ |
| การเก็บ audit | ข้อความ name/date/email ในเซลล์ | decided_by_employee_id, decided_at และคอลัมน์ยกเลิกใน HRM พร้อม Calendar description |
| ลำดับการส่ง | เรียก LINE/Calendar ตรง | บันทึก DB ก่อนแล้วทำงานผ่าน outbox อาจช้าหรือเปลี่ยน reply เป็น push เมื่อ token หมดอายุ แต่ไม่แจ้ง Calendar สำเร็จก่อน provider ยืนยัน |
| ข้อผิดพลาด/การกดซ้ำ | บางจุดไม่ได้ตรวจสิทธิ์หรือกันซ้ำ | ตรวจ signature, permission, อายุ state 30 นาที, draft/revision และ idempotency อาจปฏิเสธปุ่มหรือข้อความเก่าที่ต้นฉบับยอมรับ |
| ข้อความยืนยันนัดหมายยาวมาก | ต่อสถานที่กับข้อความแล้วส่งเป็น bubble เดียว อาจเกิน LINE limit | แบ่งข้อความยาวเป็นหลาย bubble โดยไม่ตัดข้อมูลหรือแบ่ง emoji กลางตัว ข้อความปกติคงเดิม |

## ลงทะเบียนและสิทธิ์

ระบบใหม่ไม่เขียนทับ line_uid ของพนักงานที่เชื่อมกับ LINE อื่นแล้ว และไม่ย้าย LINE เดิมไปพนักงานอีกคนผ่านการกรอกรหัส ต้องให้ HR ตรวจและเปลี่ยนข้อมูลอย่างชัดเจน มี rate limit 5 ครั้งต่อ 10 นาทีต่อ LINE user เพื่อลดการลองรหัสจำนวนมาก

ยังใช้เงื่อนไขบัญชี HRM: users ต้อง active, พนักงานไม่ถูก offboard และบัญชีไม่ค้างบังคับเปลี่ยนรหัสผ่านก่อนใช้งาน bot เป็นข้อจำกัดที่เพิ่มจากต้นฉบับที่อ่านเพียงชีตพนักงาน ไม่ได้เปลี่ยน users/password หรือสร้างบัญชี HRM ใหม่จาก LINE

รหัสพนักงานไม่ใช่ความลับและไม่ใช่หลักฐานยืนยันเจ้าของบัญชี การใช้ code-only เป็น flow ที่ผู้ใช้ระบุ หากผู้รู้รหัสไปเชื่อมก่อนเจ้าของยังมีความเสี่ยง ต้องควบคุมสมาชิก LINE OA และให้ HR ตรวจ line_uid โดยเฉพาะบัญชีผู้อนุมัติ ข้อความนี้ไม่อ้างว่า code-only มีความปลอดภัยเท่าการยืนยันตัวตนด้วยรหัสลับ

ตาราง line_link_codes ที่เกิดใน migration 0028 เป็นของวิธีเดิมที่ยกเลิกแล้ว ไม่มี endpoint ออกรหัสหรือปุ่มขอรหัสเหลือใน runtime แต่ยังไม่ drop ตาราง/migration เพื่อไม่ทำ destructive migration กับ deployment ที่อาจใช้ revision ก่อนหน้า

## Calendar และข้อมูลเก่าที่ยังไม่เหมือน

- รายการดู/ลบยังจำกัดเฉพาะ event ที่มี mapping และเป็นของ caller ไม่รวม Calendar เดิมทั้งหมดหรือรายการของผู้อื่น
- ปุ่ม ลบ บนการ์ดส่งข้อความ ลบ : ชื่อ แบบเดิม และรองรับการพิมพ์ชื่อพร้อมวันที่ แต่ชื่อซ้ำจะให้ระบุให้ชัดแทนเลือก event แรกโดยอัตโนมัติ
- ไม่อนุญาตให้ลบ Calendar ของใบลาผ่านเมนูนัดหมาย ต้องจัดการสถานะผ่าน HRM ส่วนสิทธิ์ผู้ดูแลทั้งปฏิทินยังต้องยืนยัน
- แสดง carousel สูงสุด 10 รายการตามเดิม ส่วนรายชื่อลบแบบข้อความจำกัด 100 รายการและความยาวข้อความตาม Messaging API
- ใบลาครึ่งวันจากเว็บ HRM ยังไม่ sync Calendar อัตโนมัติจนกว่าจะยืนยันช่วงเวลาทำงาน; flow LINE เดิมยื่นเต็มวัน
- ยังไม่ได้ย้าย Sheets, register fallback, Calendar ownership/iCalUID และ row mapping จึงไม่รับประกันปุ่มที่ส่งจากระบบเก่าก่อนย้าย
- ยังไม่ได้ตั้ง credentials/scheduler, ทดสอบ LINE/Calendar จริง, เปลี่ยน webhook, migrate ฐานจริง หรือ Deploy เปิดใช้งาน

## การตรวจความเหมือนของ Flex

ทดสอบ payload JSON กับ builder จากไฟล์ต้นฉบับจริง โดยใช้ fixture เดียวกันและ normalize เฉพาะ metadata ภายในปุ่ม จึงตรวจพบการเปลี่ยนสี label spacing และ field ที่หายได้ การ render บน LINE จริงแต่ละเครื่องยังต้องทดสอบหลังตั้ง test channel ไม่ใช้ผล unit test อ้างว่า live flow ทั้งระบบเหมือนเดิม 100%

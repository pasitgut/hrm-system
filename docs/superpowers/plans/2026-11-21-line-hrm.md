# LINE Bot HRM Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** ย้าย LINE Bot จาก Apps Script มาใช้งาน HRM backend บน Vercel และ Supabase ฐานหลัก โดยรักษา flow เดิมและเชื่อม Calendar ด้วย Google Service Account

**Architecture:** เพิ่ม LINE webhook ใน backend HRM เดิม แล้วเรียกกฎงานเดียวกับเว็บ บันทึก state และงาน integration ใน PostgreSQL เพื่อรองรับ webhook ซ้ำและการ retry ใช้ Google Calendar API โดยตรงโดยไม่เก็บ Apps Script เป็นตัวกลาง

**Tech Stack:** TypeScript, Node.js LTS, Vercel Functions, Supabase PostgreSQL, `@line/bot-sdk`, `googleapis`; ใช้ framework, DB client/ORM และ test runner ของ HRM เดิม หากไม่มี DB client ใช้ `@supabase/supabase-js`; หากไม่มี test runner ใช้ Vitest ไม่สร้าง Next.js app ใหม่เพียงเพื่อรับ webhook

**Spec:** [LINE Bot HRM Design](../specs/2026-11-21-line-hrm-design.md)

**สถานะ:** แผนงานเอกสาร ยังไม่ได้เริ่ม implementation ผู้ใช้มอบหมายให้เลือก stack ยืนยัน Google Service Account และให้ใช้ schema HRM ที่แนบมาแล้ว ยังไม่มี repository HRM, lookup seeds หรือ RLS policies จริงใน workspace

**Database baseline:** [HRM schema 24 tables และ 8 enums](../specs/hrm-schema.dbml) ต้องเทียบกับ `lib/db/schema.ts` ก่อน migration ใช้ฐานและตารางเดิม ไม่สร้างฐาน HRM ใหม่

## Global Constraints

- ผู้ใช้ประมาณ 10–20 คน ใช้งานภายใน ไม่มีหน้าเว็บใหม่สำหรับ bot และต้องการไม่มีค่า Deploy เพิ่ม
- ใช้โปรเจกต์ Vercel และ Supabase ฐานหลักของ HRM ไม่สร้างระบบ HRM หรือกฎอนุมัติชุดที่สอง
- ใช้ Google Service Account เท่านั้น ไม่เปลี่ยนเป็น OAuth ของบุคคลหรือ domain-wide delegation โดยอัตโนมัติ
- ใช้ `Asia/Bangkok`; timestamp ใช้ timestamptz และวันลาเต็มวันใช้ date ตาม schema HRM
- conversation state หมดอายุหลังไม่ใช้งาน 30 นาที; รหัสเชื่อมบัญชีใช้ครั้งเดียวและหมดอายุ 10 นาที
- retry สูงสุด 5 ครั้งหลังความพยายามแรก; ข้อมูล operational ที่จบแล้วเก็บไม่เกิน 7 วัน ส่วนข้อมูล HRM ใช้ retention เดิม
- ไม่เพิ่ม Redis, message broker, microservices, AI chatbot หรือ ORM ใหม่เมื่อ HRM มีของเดิม
- ห้าม commit token, service-account JSON/private key, production payload หรือ backup จริง
- ไม่มีการส่ง LINE หรือแก้ Calendar จริงใน automated tests ใช้ fake providers และฐานทดสอบ
- ทุก task ที่เปลี่ยน non-trivial logic ใช้ red/green tests และ commit หลังผ่าน โดยทำใน repository HRM จริงเท่านั้น
- Task 0 ต้องยืนยันไฟล์และสัญญา HRM ก่อน Task 1 ห้ามใช้โฟลเดอร์ Apps Script นี้สร้าง HRM ใหม่ทดแทนโดยไม่ตั้งใจ
- ใช้ employees.line_uid และ line_webhook_events เดิม ห้ามสร้าง link table/inbox ซ้ำ และห้ามเปลี่ยนความหมาย sheet_committed/response_payload/status/attempts ที่ handler เดิมใช้
- RLS เปิดอยู่ตาม schema แต่ยังไม่ทราบ policies; users.password_hash ไม่ได้ยืนยันว่าใช้ Supabase Auth ห้ามสร้าง auth.uid() policy จากการเดา
- work tracking, OT, assets, Google Drive และ Cloudinary เป็นระบบเดิมนอก scope ต้องคงการทำงานและสิทธิ์เดิม

## Review Focus

1. วันลาเต็มวันข้ามสิ้นปี/ปีอธิกสุรทิน และเวลาที่มี offset ต้องได้วันและเวลาตาม Bangkok; ทดสอบใน Task 6 และ 8
2. webhook เก่าหรือมาผิดลำดับหลัง state หมดอายุ ต้องไม่ย้อนบทสนทนาหรือส่งคำขอเก่า; ทดสอบใน Task 3–4
3. พนักงานถูกปิดบัญชีหรือถอนสิทธิ์หลังส่ง Flex แล้ว ต้องทำ action ไม่ได้; ทดสอบใน Task 5
4. provider ทำงานสำเร็จแต่ response หาย ต้องไม่สร้าง Calendar ซ้ำ และ LINE ต้องถูกจัดเป็นผลไม่แน่นอนหากพิสูจน์ไม่ได้; ทดสอบใน Task 6–7
5. ปุ่มเก่าที่อ้างอิงเลขแถวและ Calendar เดิมที่ไม่มีเจ้าของ ต้องไม่กระทำกับรายการผิดหรือถูกลบโดยผู้ไม่มีสิทธิ์; ทดสอบใน Task 6 และ 8

เสริม regression ที่บังคับจาก schema: handler work tracking เดิมต้องไม่ถูกแย่ง claim ใน line_webhook_events และ cleanup ของ bot ต้องไม่ลบ receipts งานเดิม; ทดสอบใน Task 1, 2, 7 และ 9

## Database Mapping ที่บังคับใช้

| ข้อมูลจาก bot | ตาราง/คอลัมน์ HRM | ข้อจำกัด |
|---|---|---|
| พนักงานและบัญชี LINE | employees.id, code, first_name, last_name, line_uid | code เป็น varchar(4) และ line_uid unique; ใช้ UUID พนักงานเป็น FK |
| actor และสิทธิ์ | users.employee_id, role, permissions, is_active; employees.deleted_at/end_date/employment_status_id | อ่าน policy เดิม ไม่ถือว่า hr/executive/manager อนุมัติได้ทุกคนอัตโนมัติ |
| ประเภทลา | leave_types.code, is_active, annual_quota_days, quota_basis | quota_basis fixed/tenure ต้องคำนวณผ่าน HRM |
| ใบลา | leave_requests.id, employee_id, leave_type_code, start_on, end_on, session, reason, status_code | date-only, session default full; ค่าอื่นใช้ได้เมื่อ service ยืนยัน |
| ผลพิจารณา | decided_by_employee_id, decided_at, decision_note | อ่าน/เขียนผ่าน service HRM |
| ยกเลิก | cancelled_by_employee_id, cancelled_at | ต้องตรวจ actor และสถานะปัจจุบัน |
| รหัสสถานะ | request_statuses.code | schema ยืนยันเพียง pending เป็น default ต้องอ่าน seed สำหรับสถานะอื่น |
| รับ webhook/กันซ้ำ | line_webhook_events.event_id, source_id, status, attempts, lease_until, response_payload, error_code, push_retry_key | ใช้ของเดิมและตรวจเจ้าของ pipeline; ห้ามสร้างตาราง receipt คู่ขนาน |

leave_requests ไม่มี source/version column แผนนี้ไม่เพิ่มเพียงเพื่อให้ตรง interface ที่เสนอ ใช้ status_code และ updated_at ใน conditional update ตาม precision ของ DB และใช้ operation key คงเดิมต่อ ID/action สำหรับ jobs ค่า resourceVersion ใน interface ด้านล่างเป็น opaque token จาก service เช่น updated_at ที่อ่านจาก DB ไม่ใช่คอลัมน์ version ที่สมมติขึ้น และไม่ใช้ token นี้แทน event ID สำหรับ deduplication

ก่อนเพิ่ม bot state, account-link challenge, jobs, Calendar mapping และ legacy mapping ให้ตรวจ repository ว่ามีอยู่แล้วหรือไม่ สิ่งที่ไม่ปรากฏใน DBML ไม่ได้พิสูจน์ว่าไม่มีในระบบจริง เพิ่มแบบ additive เฉพาะส่วนที่ขาด และคง schema/migration workflow ของ lib/db/schema.ts

## ลำดับและจุดหยุด

Task 0 มาก่อนทั้งหมด จากนั้น Task 1–7 ทำตามลำดับ Task 8 ใช้ผลของ Task 1, 5, 6 และ 7 และ Task 9 เป็น gate ก่อนเปิดจริง แผนนี้เป็นงาน integration เดียว ไม่แยก deploy subsystem ที่ยังทำงานไม่ครบ

หาก Task 0 พบว่า HRM เป็นระบบที่แก้ backend ไม่ได้ ให้หยุดส่วน implementation และแก้แผนเป็นโปรเจกต์ Vercel แยกที่เรียก HRM API ห้ามข้าม business rules แล้วเขียนฐาน HRM ตรงเพื่อให้ bot ทำงานได้เร็วขึ้น

- Calendar ใช้ Service Account ที่มีสิทธิ์จริง ไม่ต้องใช้บัญชี Google ของพนักงานแต่ละคน
- งานค้างตรวจและกู้ได้ มีเจ้าของตรวจ failed/unknown jobs และมี retention/backup ตามนโยบาย
- โควตาและสิทธิ์แพ็กเกจถูกยืนยันกับ environment จริง ไม่มีคำรับรองว่าใช้ฟรีโดยอาศัยจำนวนผู้ใช้เพียงอย่างเดียว

## การตรวจแผนก่อนส่ง

ตรวจความครอบคลุมกับ Spec: scope/stack และจุดเชื่อมอยู่ Task 0; persistence/สิทธิ์อยู่ Task 1, 4, 5; webhook/state อยู่ Task 2–4; Calendar อยู่ Task 6; retry/retention อยู่ Task 7; migration/legacy อยู่ Task 8; acceptance/cutover/rollback อยู่ Task 9

ตรวจชื่อ interfaces ต่อเนื่องระหว่าง tasks และกำหนด Review Focus ทั้งห้าเรื่องรวม regression ของตาราง LINE ร่วมลงใน tests แล้ว ชื่อตารางและชนิดข้อมูลยึด schema ที่ผู้ใช้ให้ ส่วน ORM, policies, lookup seeds, router และ API จริงยังเป็น gate ใน Task 0 ไม่ให้ implementer เดาและสร้างระบบใหม่เอง

ยังไม่ได้รันทดสอบ application หรือ deployment จากแผนนี้ เพราะเป็นงานเขียนเอกสาร และยังไม่มี repository HRM สำหรับ implementation


## สถานะ implementation หลังตรวจ repository จริง

ใช้ path จริงและเจ้าของแต่ละหน้าที่ตาม `docs/integrations/line-hrm-map.md` ซึ่งแทน File Map เชิงข้อเสนอข้างต้นในจุดที่ต่างกัน โค้ดไม่เพิ่ม SDK/ORM เพราะใช้ Drizzle/postgres, jose, crypto/fetch และ Zod เดิมได้

- Task 0: ตรวจ source/schema/seeds/permissions และทดสอบ local แล้ว; สิทธิ์/โควตาบัญชี production ยังเป็น deployment gate
- Task 1–5: เพิ่ม persistence, signed webhook, conversation, account linking และ shared leave commands แล้ว พร้อม regression tests
- Task 6: เพิ่ม Google Service Account adapter และ Calendar jobs แล้ว; live provider และ legacy/half-day policy ยังอยู่ในรายการรอ
- Task 7: เพิ่ม durable job recovery, retry และ cleanup แล้ว; การตั้ง scheduler บัญชีจริงยังรอ deployment owner
- Task 8: การนำเข้าข้อมูลจริง/legacy mapping ยังไม่เริ่ม เพราะไม่มี export และข้อมูลยืนยัน ปุ่ม row เดิมถูกปฏิเสธอย่างปลอดภัย
- Task 9: ตรวจ local test suite/typecheck/build; production deployment, provider smoke tests และ cutover rehearsal ยังไม่ดำเนินการ

รายละเอียดทุกส่วนที่ติดหรือเลื่อนไว้: `docs/line-bot-pending.md`; ข้อวินิจฉัยและผล review: `docs/line-bot-implementation-review.md` ห้ามอ่านสถานะ local validation ว่าเปิด production แล้ว
